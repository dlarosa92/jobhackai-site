# JobHackAI business dashboard

Private Cloudflare Worker for `dashboard.jobhackai.io`, protected by Cloudflare Access. Owner decisions remain owner-only; explicitly configured machine identities have limited preparation and reconciliation capabilities.

Read the versioned [operating guide](OPERATING-GUIDE.md) and [API contract](API.md) before changing records or coordination. These replace older board and workload instructions.

## Sources and refresh

- Payment and user numbers are read from production D1. User records do not mean paying customers. Owner-entered monthly costs live in separate dashboard D1; income is an estimate, not reconciled accounting.
- Every card opens the same in-dashboard review panel. Complete verified snapshots expose Approve, Request changes and Decline. Approval binds exact copy, destination, media, links and timing; sending or scheduling remains separate. Summary-only legacy approval endpoints are retired; past decisions are retained.
- Cards name the real channel (Email, LinkedIn, Pinterest, Facebook, Instagram, X, Nextdoor or Blog). Filters count saved cards, including batch records; they are not message or impression totals. A zero means no saved records for that platform, not proof of no activity.
- Your next decisions comes first. The board groups Ready for your review, In progress and Up next; Waiting or blocked and Completed activity start collapsed. Marketing, Sales & Outreach and Product & Technology contribute to one backlog. Source status and approval remain distinct.
- The existing hourly preparation and half-hour reconciliation workflows import verified source drafts into dashboard D1. Page/chat text is not an automatic feed: the “Is work moving?” panel shows actual run receipts, missed runs and overdue owner feedback. Source freshness alone cannot make execution healthy. A broad group approval must not be inherited by a later replacement draft. Preserve decisions and native receipts when reconciling a conflict.
- Tracked Gmail conversations come from a standalone Google Apps Script. See [installation and operating instructions](google-apps-script/README.md). The last non-draft message determines whether a conversation needs review or is waiting for its recipient. Only minimal metadata is stored; Gmail access stays with Google.
- Directory requests are read directly, read-only, from production `directory_requests` on every board refresh. They do not depend on successful email delivery, Gmail labels or the Gmail scan. Cards show the submitted contact address and full details, clearly marked unverified. The newest 200 submissions are loaded with an explicit warning if older history exists. A source failure is displayed, never reported as an empty current queue.
- **Mark reviewed** stores an owner decision in dashboard-only `board_resolutions`, bound to the exact Gmail message ID or directory content/review revision. Refresh, relabelling and repeated syncs cannot reset it. A new message or changed request becomes active again; notification-delivery retries do not. **Reopen** reverses a dismissal. Handled history remains visible separately. Neither action sends, deletes mail, approves a listing, changes production directory review status or clears bounce/opt-out restrictions.
- Directory intake replaces a matching manual `local-request-<reference>` card and an exact JobHackAI noreply notification with that reference; later business replies remain separate tracked conversations. It never deduplicates by person or business name.
- Customer-impacting failures and commitments rank first, followed by software growth toward 250 users and verified revenue. Shared dependencies are ordered before dependent work. Selected conversations default to prospect; explicitly recorded customer classifications are preserved by sync.
- Page load, return to the tab and Refresh reload board records. Visible tabs check the transactional board revision every two seconds; saved actions refresh work immediately. A one-minute refresh also updates metrics and external directory reads. Google independently checks the label approximately every five minutes. The UI displays the actual last successful Gmail scan and warns after 15 minutes without success. Refresh cannot reset Gmail freshness.
- Tracked Gmail sync does not alter approvals. The separate outreach gate requires exact copy approval, current first-party evidence, working MX targets and all-folder Gmail checks. Initial sender activation requires the owner’s separate Gmail send-permission approval. Preserve a later authorized activation; do not toggle live permissions to match old installation prose. An enabled sender is never approval for a particular message.
- GA4 aggregate reports are imported by the existing reconciliation workflow once each Eastern day, using the rolling 28 days through yesterday. The API rejects frozen historical dates and stale observations. Missing imports stay visibly stale; campaign coverage, staff exclusions, attribution and collected purchase reconciliation remain explicit independent limitations. This is an authenticated source-read workflow, not a new direct GA OAuth integration or synthetic event test.
- Every owner approval or request-changes decision creates a durable departmental handoff in the same database transaction. Claims expire after one hour, changed copy requires a new decision, and the old decision remains immutable. Follow-up completion requires a current complete packet; it never performs external release. A server cron checks run and handoff deadlines every 15 minutes, independently of the Mac.

## Outreach quality gate

Prepare one exact researched plain-text message through **Add a prepared email for review** or owner- or preparation-machine-authenticated `POST /api/outreach/prepare`. Include a stable ID, lane, phase, complete email with visible URLs, and current first-party published-contact/business-fit evidence. Local providers require their actual directory profile. Do not submit HTML automatically. A necessary formatted variant must include a specific `formatRequest.reason`; it remains held until the owner approves that exact revision through `POST /api/outreach/format-approve`. Machine identities cannot make this decision. The owner sees the reason, plain-text fallback and sandboxed formatted preview. Current routing and Gmail checks plus any required format decision must pass before exact copy approval. Approval has no sending effect; release is separate and rechecked. The exception reason is revision-bound; unchanged plain-text hashes and historical receipts remain compatible.

`node scripts/routing-preflight.mjs packet.json` checks each recipient domain and its MX targets' A/AAAA resolution. Exit 0 means routing present, 1 means at least one hold/reject, and 2 means invalid input. Input is a private JSON `messages` array, each with `recipient` (or nested `message.recipient`). Never commit contact packets or diagnostics. DNS results are not mailbox or inbox verification.

Durable native bounce/reply suppression, business and recipient deduplication, conservative five-complete-business-day follow-up timing, exact original-thread matching and one atomic attempt prevent stale approvals or ambiguous send retries from releasing new outreach. Legacy generic email approvals stay in history but cannot authorize the guarded sender. Stan supplies evidence and Marblism-prepared copy; Codex independently checks and submits it; Sebastian approves exact copy and separately requests release. See the [relay upgrade and optional sender activation](google-apps-script/README.md).

Tests cover these failure cases with real SQLite, mocked public DNS and an Apps Script VM; no test sends external mail. The standard Gmail manifest remains read-only.

## Team work board (Option C)

The mobile view starts with four KPI cards, one owner action and three priority cards. Desktop uses Needs you / Working / Waiting / Done columns. The full backlog preserves the server's dependency-aware ordering. Filters cover department, Core/Local and platform. Dark mode is the default; the light/dark choice stays in local storage. Metric help works by hover, keyboard focus and tapping the question mark. Long plans, drafts, source notes and scheduled-run receipts are collapsed.

`overview.business` contains independent 7-day and 28-day comparisons, using complete Eastern calendar days ending yesterday. Payment history reads production live USD captures and succeeded refunds; accounts use creation time; finished interviews use scored text records and completed voice records. These read-only, bounded queries need no migration. A failed query returns an unavailable metric, never zero. Raw account/interview counts still include staff and tests. The current paying-customer stock and the 250-user goal remain unverified until paid access and exclusions are checked. There is no new Stripe API credential or GA4 integration in this release. Daily sparklines are reconstructed from saved dates, not overlapping GA4 reports.

Approval remains separate from execution. **Approve draft** saves a decision and the existing owner handoff. **Queue approved email** requests the existing guarded sender, and is disabled when that sender is unavailable. Other channels show **Review send step** or **Review publishing step** with the actual connection limit. Queued, scheduled and unknown results never display as sent/published. An open review keeps its note and disables its old actions if the saved revision changes.

New workflow write receipts use `progressBasis: deliverable-v1`. Only a changed draft's copy/destination/timing/media/links or a recorded scheduled/published/sent/closed milestone counts as advancement. Changes to instructions, priorities, evidence wording, source revisions or check times do not. Older receipts are not backfilled as progress. Move history begins with the new receipts and says so on the board. Existing local schedules and Cloudflare's independent 15-minute deadline monitor continue; no new scheduled chats or external sends are created by this UI release.

Dashboard state integrity requires `007-dashboard-integrity.sql` before deploying both Workers, then `008-dashboard-change-triggers.sql` after both accept trigger-inclusive D1 change counts. It separates verified execution receipts from editable preparation notes and maintains a transactional board revision for live updates. Read the immediate-completion contract in `API.md` before integrating an executor. A two-second board poll does not make an unconnected external platform instantaneous; the executor must deliver its receipt immediately after native verification.
