# Durable deletion recovery — integration in progress

The prior handler could remove Firebase sign-in and then fail to delete stored content or KV payloads without a durable retry path. This draft now wires the authenticated delete endpoint to durable intent, manifest preparation, exclusive execution, verified provider phases and retryable cleanup. API and signed-webhook admission are wired. Scheduled recovery, worker coordination, live-session handling, uncertainty reconciliation and notification delivery remain unfinished, so this is not a completed release. Migration 028 remains unapplied and must precede deployment.

Migration 028 creates a job outside the users foreign-key tree. Its initial snapshot contains the verified UID, original D1 user ID, notification email and KV keys. It deliberately stores no bearer token, Firebase service credential, resume text, interview transcript or scorecard. Preparing the job must succeed before billing or identity side effects.

The storage helper has four phases: prepared, billing_verified, identity_removed and complete. Only the caller that has actually confirmed billing and Firebase results may advance it. A crash or timeout during identity deletion leaves billing_verified; recovery must reconcile the identity instead of inferring success. This phase record does not itself perform those provider operations or certify their outcome.

For an identity-confirmed job, cleanup first makes its storage-key manifest durable and writes the authoritative deletion tombstone. It deletes each KV key without swallowing errors. A failed key leaves every D1 content reference and the job available for retry. A single D1 batch then removes content, the account, consent-owned campaign links and queued Analytics delivery, and records completion. A failed statement rolls back the entire batch. Payment/refund/ledger records remain financial history. Completion clears the recovery email and storage paths; the operational UID receipt and existing fraud-prevention tombstone remain.

The final transaction checks UID/user-ID ownership again; a changed owner rolls back erasure. This is defense against stale recovery data, not an application-wide write lock. New requests, pending Checkouts and webhook races still require the integration below.

## Admission primitives added September 20

The same unapplied migration 028 now also defines durable deletion intents and operation claims. A deletion intent immediately prevents new admitted operations; manifest creation and each recovery phase require all earlier operations to finish. The insertion predicate and deletion-intent insert are serialized by D1, covering either order without an unlocked check-then-write. Completed intent markers survive erasure so an old token cannot acquire a new claim. Completion clears the intent email and finished claims in the same erasure transaction.

Crashed or uncertain operations do not silently expire. There is deliberately no public or automatic "mark finished" escape for an uncertain provider request. The recovery integration must reconcile that request before deletion can proceed. These primitives are not yet an application-wide protection: authenticated API middleware and its background work are now covered, and account creation and signed webhook handling are now covered below. Scheduled/background workers and runner integration still need protection before deployment. Real SQLite tests cover both operation/deletion orderings, earlier operations, permanent uncertainty, UID isolation, retry identity, missing schema, and manifest/phase refusal without quiescence.

The runner design should reuse the application's already-configured provider credentials through an authenticated internal recovery endpoint where possible. It must not copy user tokens into jobs. Any internal invocation credential, bounded scheduling, replay protection and audit mode still require implementation and verification; no worker or new integration has been configured.

## Checkout and payment guard added September 20 (draft, not deployed)

The existing deletion billing helper now scans paginated Checkout Sessions and PaymentIntents for each candidate customer before its first mutation. Active checkout ownership requires the verified customer and session UID, no conflicting client reference, and the correct environment. A setup-mode session, unknown state, completed-but-unpaid checkout, or unsettled payment blocks deletion. It never cancels a pending charge. The only active payment permitted before expiration is a not-yet-started payment explicitly attached to a verified open checkout; a second scan must observe settlement afterward.

Every owned open checkout must return a matching expired session. Expiration timeouts or errors do not imply success. Fresh session/payment/subscription scans follow expiration, and another scan follows subscription cancellation. The route's failure message discloses that some subscriptions may already be canceled and checkouts expired. Sign-in removal remains after this helper succeeds. Historical paid/expired sessions and succeeded/canceled payments do not block deletion solely for lacking legacy metadata.

This strengthens the existing request handler in this draft, but is not a global lock: admission must still cover all request/background writers and webhook behavior before deletion can be promoted. The billing tests include pagination, ownership conflicts, pending payment states, false expiration successes, timeouts, a subscription appearing during expiration and a payment appearing after cancellation. The additional invoice/schedule checks cover pagination, malformed/foreign resources, API failures, settled history and resources appearing after cancellation. Together with the 18 SQLite admission/recovery tests, 73 focused checks pass locally. No Stripe call or real customer deletion was performed by these fixtures.

## Authenticated request and background admission wired in the draft

`api/_middleware.js` verifies bearer identity and acquires a durable operation claim before running any authenticated API handler, including GET handlers that can write. Deletion bypasses ordinary admission to avoid waiting on its own claim; its handler now runs the intent/processor below. Anonymous endpoints and scheduled jobs keep their own authentication and still need their appropriate writer coordination. Signed Stripe webhooks now have resolved-owner admission as described below. Missing schema fails closed, so this draft must not be deployed before the explicit migration and completed integration.

`account-operation-scope.js` keeps the claim active through the full handler and registered background work. Voice scorecards, checkout welcome emails and lead-magnet background work use a task factory registered through shared Pages `context.data`. A child handler has its own context; replacing the parent's `waitUntil` would miss it. Nested work is drained before settlement. A late task cannot start after settlement. Handler exceptions, server failures and rejected background work retain uncertain claims, and a crash or failed settlement leaves active claims requiring reconciliation.

Checkout, upgrade, cancellation and portal handlers pass a request-local environment observer to the common Stripe adapter. A mutating Stripe call that times out, throws or returns 408/429/5xx remains uncertain even if an endpoint catches that failure or maps it to a successful/client-error response. This does not mutate the shared environment or use global request state. Successful or definitively rejected calls can finish. Resolving uncertain claims, external portal/dashboard mutations and in-progress live voice connections remain part of the recovery integration; a successful HTTP response is not proof that every external business operation has ended.

The existing 73 deletion/admission/recovery checks and full billing suite also pass. A separate test builds the actual Pages Worker and uses a signed local JWT plus intercepted JWKS to verify real middleware routing, both checkout routes and security headers with no external request. CI now builds and tests that candidate bundle separately. Voice usage/reservation and portal ownership checks pass; no production, QA migration, actual interview, Stripe mutation or live deletion was performed.

## Atomic account-creation fence added September 20

The shared `getOrCreateUserByAuthId` now creates a missing account with one `INSERT ... SELECT ... WHERE NOT EXISTS` statement that checks both durable deletion admissions and the existing UID tombstone table. An intent or tombstone inserted after the initial missing-user read therefore prevents recreation. Completed admission receipts also prevent recreation even if a tombstone is absent. Missing guard tables fail closed, including on the legacy users-schema fallback. This adds migration 028 as a requirement for account creation in this draft; it remains unapplied and the draft must not be deployed yet.

Six real SQLite tests run the actual helper, including an injected intent or tombstone precisely between the absent-row read and insert, completed receipts, UID isolation, creation-first ordering with an active admission, missing guard tables, and the legacy schema fallback. All 93 focused deletion/admission/recovery/creation checks and the full billing suite pass locally. The test also exposed the old fallback's failure to recognize SQLite's `no column named last_login_at` message; that fallback now recognizes only the specific missing activity column and preserves both guards.

This fence covers new-row creation. Returning or updating an existing row still needs the full-operation admission provided by authenticated API middleware and now by signed-webhook admission; worker writers still need equivalent protection. It does not establish that delayed webhook updates, external billing changes, recovery scheduling or completion notifications are finished. No migration, deployment or live deletion was performed.

## Signed webhook admission wired in the draft

After signature, environment, idempotency and owner verification, each entitlement/dunning handler obtains a durable claim for its resolved UID before any account creation, update, usage reset or email preparation. This covers completed/async-paid Checkout, subscription creation/update/deletion and failed invoices. Deletion intent makes a later entitlement event a recorded no-op. A prior webhook holds deletion until its D1 batch, awaited cache operations and registered background work settle. Legacy D1/KV tombstones are checked even when a users row still exists, and missing D1 tombstone/admission schema fails closed.

The existing unapplied migration 028 now also records the Stripe event ID on a webhook claim, allowing future reconciliation to identify the corresponding durable ledger event without storing its payload. Server/critical failures and rejected or failed post-commit work preserve uncertainty; a crash or failed settlement retains an active claim. Claims never expire into assumed safety. Acknowledging an already-committed event does not discard an unfinished claim. Nested background tasks are drained, and no new task can start after the scope closes.

Captured payments and refunds remain a separate financial-only path. They do not create users or acquire account claims. Their campaign-link statement reads the still-existing consent-owned checkout rows inside the same atomic financial batch. SQLite tests run actual recovery and then deliver a late refund: money history updates, but user, consent, campaign and Analytics-outbox rows remain erased. A second test pauses a financial event after staging, completes erasure, then commits the financial batch; it retains money without restoring campaign links. These fixtures make no real payment, provider call or email delivery.

Sixteen added SQLite/actual signed-handler checks cover both event/deletion orderings, every entitlement/dunning route, existing-row tombstones, delayed batch/cache/email work, owner conflicts, mode isolation, missing schema, failed writes/settlement/background work, event-ID provenance, nested work and the two financial-history races. All 109 focused local checks and the full billing suite pass. Candidate compilation and CI remain separately recorded in the release evidence.

This completes signed-webhook admission in the draft, not the overall recovery release. Remaining work includes bounded scheduled recovery, uncertain-operation reconciliation, worker integration, external billing/live-session coordination, completion notification delivery and deployed disposable-account QA. ## Durable delete endpoint and identity reconciliation wired in the draft

The authenticated POST handler now takes the UID only from the verified Firebase token, creates a durable deletion intent, waits for admitted work, snapshots references, and invokes the recovery processor. A job uses the same reference as its intent. The original best-effort post-identity erasure path and bearer-token deletion fallback have been removed from this endpoint. A successful provider operation never substitutes for the completed storage transaction.

The processor validates its configured Firebase service account against FIREBASE_PROJECT_ID before accepting a new intent. It imports the signing key locally, uses project-scoped Admin calls with the verified UID, and keeps credentials/tokens in memory only. Billing must be confirmed before identity removal. A fresh identity lookup follows every delete attempt, including errors/timeouts. A retry in billing_verified first checks whether identity is already absent; if so, it resumes cleanup without repeating billing or identity mutations. If identity still exists, billing is checked again before deletion. Provider payloads and diagnostics are never returned to the user.

Execution uses a durable exclusive token. Concurrent retries cannot both run providers. Normal completion or a handled pending result releases only its own token; a crash or failed release leaves it for explicit reconciliation. No age or lease timeout grants permission to take over. The future runner/reconciliation path must address interrupted executions before this can be promoted. Identity-removed storage retries need no Firebase/Stripe credentials, and completed jobs return their receipt without contacting providers.

HTTP 200 means the content erasure transaction completed. HTTP 202 means the request is saved but unfinished, with a reference and a coarse explanation; it does not assert completion or automatic recovery. Identity removal can be confirmed true, confirmed false, or unknown. The account UI keeps the local session and offers Check Deletion Status while removal is unconfirmed. It signs out only after confirmed removal and explicitly surfaces pending storage cleanup. Unexpected failures return a generic 503 rather than internal SQL/provider errors.

Migration 028 also includes a notification outbox. The final erasure transaction copies the notification address into its pending record before clearing the manifest, once per job. The sender, provider idempotency and address-retention policy remain required; no completion email has been sent by this draft. A database failure staging the notice rolls back the whole erasure transaction, preserving references for retry. A future delivery failure must never reverse completed erasure.

Sixteen new checks exercise the actual processor with real SQLite and intercepted Stripe/Firebase HTTP, including genuine local RSA signing of fixture OAuth assertions. They cover manifest-before-provider order, billing failure, earlier work, simultaneous retries, crash tokens, ambiguous identity results, phase-persistence failure, cleanup retry without provider credentials, notification transaction failure, project mismatch, malformed/foreign identity responses, verified-UID routing, response privacy and the actual pending UI handler. These replace five obsolete best-effort route mocks; the existing 50 billing-safety checks remain. Current focused total: 120. Full billing regression and candidate build/CI results are recorded separately. No live deletion, migration, credential entry or real email occurred.

Provider protocol checked September 20: [project-scoped account lookup](https://docs.cloud.google.com/identity-platform/docs/reference/rest/v1/projects.accounts/lookup) and [project-scoped account deletion](https://docs.cloud.google.com/identity-platform/docs/reference/rest/v1/projects.accounts/delete). Both require Google OAuth credentials and permissions on the target project; the code additionally pins that project to the application's Firebase setting.
